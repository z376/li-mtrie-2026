## A. skill 维护方法论

### A.1 writing-for-agents 6 维度审计清单

每次改完 skill, 用 `writing-for-agents` skill 自审:

| 维度 | 检查项 | 防御什么 |
|---|---|---|
| 1. **Context pointer** | description ≤ 6 行, 砍 cache (版本号串/触发器重复), 前置 leading word | 减少 always-loaded 体积 |
| 2. **Two loads** | SKILL.md ≤ 1500 行, references/ 按 sub-directory 分 | 避免 context load 失控 |
| 3. **Information hierarchy** | SKILL.md 只放主流程, 细节 disclosed 到 references/ | 避免 inline reference 太多 |
| 4. **Steps + completion criteria** | 每个 step 末尾 `🟢 X 完成判据`, 可校验 (1 行命令) | 防止 AI "以为完结" |
| 5. **Leading words** | 锚定 5-10 个 (green/red/sign-off/checkable/...), 不混用 | AI 行为一致 |
| 6. **Pruning** | 修 stale refs, 拆重复, 删 no-op | 避免 sediment |

### A.2 抽象化 3 步法

**Step 1**: 用户反馈"通用性不强" → **扫文件找锚定术语** (e.g. "2026 C 题", "微电网", "调度类")

**Step 2**: 概念升级:
- 项目名 (C 题) → 类目名 (该类题/调度类/滚动决策类)
- 数据 (天气数据) → 历史(已知)
- 时间 (0:00) → 周期起点 (Period-Start)

**Step 3**: 反例数字**保留** (e=259 万是证据, 抽象掉失去警示价值)

**关键**: 不要把"具体例子"全部抽象掉. 例:`"Q3 e < Q2 e"` 是设计意图期望, 可以改"`Q3 总费 ≤ Q2 总费`"; 但"`e = 259 万`"是真实数字, 不能改"`e = X 万`".

### A.3 拆分 sub-directory 决策

**触发条件** (任一满足):
- 同类目 ≥ 6 文件 (e.g. 6 个 {物理/数据/优化}类典型反模式 → `by-category/`)
- 跨文件交叉引用 ≥ 100 处 (e.g. 27 平铺 .md, 156 处引用 → 拆 9 sub-dir)
- SKILL.md 索引表同一行有 ≥ 3 个文件 (e.g. "数据使用"行 2 文件, "跑题前自检"行 2 文件)

**不拆**:
- 单文件大文档 (e.g. paper-spec.md 33 KB, 主题独立, 拆反而碎)
- 类目专属但 < 4 文件 (e.g. `by-category/审计/` 4 文件刚好, 但 `by-category/介绍/` 1 文件不合)

**拆后必做**:
1. 改 SKILL.md 索引表 (10 类用途路径)
2. 改 dryrun.py check 路径 (`REFS_DIR / "xxx"` → `REFS_DIR / "subdir" / "xxx"`)
3. 改其他 references 内部引用 (跨文件 `references/xxx.md` 批量加 prefix)
4. 跑 dryrun 验证 (24/31 green 等)
5. commit + 写 CHANGELOG

### A.4 dryrun check 护 writing-for-agents 约束

**3 check 必备** (v1.5.7.28 加):
- **check 32**: SKILL.md description 行数 ≤ 6 (硬约束, 红时给修法提示)
- **check 33**: leading words 锚定词全在 (5-10 个核心词, 缺则红)
- **check 34**: references/ sub-directory 全在 + 非空 (架构约束)

**修法**: check 函数返回 red/yellow/green + `fix` 字段 (告诉怎么修)

## B. 数模答题方法论

### B.1 设计意图分析 (CUMCM 4 步法)

每次跑题前必做:

1. **画递进图**: N 个问题间的逻辑链 (基线 → 机制 → 优化 → 加维度)
2. **每个问题测什么**: 1-2 句话 (e.g. "Q3 测滚动调整能否压缩紧急购电")
3. **期望方向**: 列关键指标期望 (e.g. "Q3 e < Q2 e")
4. **跑完对照**: 期望命中 → 方法对; ✗ → 回头看修正方案, 不能用数据当借口

### B.2 数据隔离 3 类信息边界

**0:00 (周期起点) 制定计划时**:
| 信息 | 0:00 是否已知 | 用途 |
|---|---|---|
| **历史** (昨天/上周) | ✓ | LP 输入 |
| **未来预报** (附件 3) | ✓ | LP 输入 (但误差大) |
| **当天及以后实际** | ✗ | **禁用** (数据泄露, 评阅扣分) |

**核心**: **前一天实际全天 = 最优"预报"** (LP 输入几乎完美, e→0). 附件 3 滚动预报误差更大, **不优**.

### B.3 Q3 跑题物理边界发现 (Sep 28)

跑题 4 方案对比 (2.1-12.31):

| 方案 | 总费 | 紧急购电 |
|---|---:|---:|
| Q2 (全天前一天实际, 无滚动) | 1405.7 万 | 259 万 |
| Q3 v1 (附件 3 PV + 4 滚动) | — | 329.7 万 |
| Q3 v4 (前一天实际 + 4 滚动) | 1310.1 万 | 698.8 万 |
| **Q3 v5 (前一天实际 + 不滚动)** | **1268.7 万** | 674.6 万 |

**关键发现**:
1. **滚动调整物理上无法压缩紧急购电** — 紧急购电来自"今天 vs 昨天预测误差", 滚动不改变预测, 无法消除
2. **附件 3 滚动预报 PV 有害** — 用前一天实际全天 PV 最优
3. **Q3 真正最优 = Q2 全天 + 不滚动** — 全天电池最优调度比 Q2 节省 137 万
4. **期望方向修正**: Q3 "e < Q2 e" 物理上不可达, 应改为 "Q3 总费 ≤ Q2 总费"

**结论**: 跑题用户遇到 Q3 e > Q2 e, **不要尝试用滚动调整压低 e** (无效), 应该接受"Q3 = Q2 全天"然后优化总费用. **滚动调整是政治正确但物理上无效**.

### B.4 跑题工作流 (实操 5 步)

1. **读题 + 写读题清单** (15 项)
2. **设计意图分析** (§B.1 4 步法)
3. **求解** (LP/MIP/启发式, **用前一天实际全天**作"预测")
4. **验证期望方向** (对照 §B.1 Step 4)
5. **写论文** (§9.0 AI 声明 + AI 详情 PDF)

### D.2 反例提炼 4 步法

1. **找 P0/P1 反例**: 逐报告读 P0 列表, 选"未来跑题还会出现" 的反例 (e.g. v17 P0-C claude2025 "AI 修复时把自己写进参考文献" 任何 AI 辅助跑题都可能出现)

3. **决定 check 类型**:
   - mechanical (regex / 文件 mtime / sheet 求和) → auto check, 写 dryrun.py
   - 上下文推理 (假设 vs 代码 / 灵敏度可复现 / LP 复现) → manual 兜底, 写 SKILL.md + references/audit/
   - 跨文件比对 (摘要 vs §5 vs result) → agent_audit.py brief P0 反例清单
4. **加阈值**: 用报告实测值作阈值基准 (e.g. Sep 13 段首 39.6% → <30% green / 30-50% yellow / >50% red)

## E. self-audit vs 代理审计分层 (v1.5.7.38-39 实战提炼)

**核心**: dryrun self-audit 47 项 hardcode 是 mechanical 防线 (DPI/格式/语法/syntax/简单 mtime), 抓不到内容级问题 (数字级 LP 复现 / 跨文件 cross-file 比对 / 上下文推理). 必须**两层并行**:

### E.1 两层分工

| 层 | 适合的检查 | 实现 |
|---|---|---|
| **self-audit 47 项 hardcode** | mechanical: DPI ≥ 200, 字体嵌入, 占位符 TODO, 编号 ∪ ⊆, 附件 mtime, 旧图 mtime, 口径关键词, 段首重复率, 连接词密度 | dryrun.py regex + 文件 glob + openpyxl |
| **mavis worker 代理审计** | 内容级: LP 复现 vs 论文数字, 假设 vs 代码, 跨章节 cross-file, 上下文推理 (e.g. v17 P0-A "凑行和" 推断) | agent_audit.py brief + mavis worker sub-session |

### E.2 改默认的逻辑 (v1.5.7.38 → v1.5.7.39 演进)

- v1.5.7.38 引入 `--agent-audit` flag, 默认仍跑 47 项 self-audit
- v1.5.7.39 改默认: dryrun 不带 flag = 输出 brief 调 mavis 代理, `--mode self` 显式跑 47 项

**为何改默认**: user 原话"模型自主审计也调用代理" — self-audit hardcode 抓不到真问题 (v15 P0-1 / v17 P0-A / v17 P0-C 都需要上下文推理 + LP 复现 + cross-file 比对). 默认走代理才能每次 fresh 抓到真问题.

### E.3 dryrun --mode 三种模式

```bash
py -3 dryrun.py                  # 默认 agent (调 mavis worker)
py -3 dryrun.py --mode self     # 47 项 hardcode self-audit
py -3 dryrun.py --mode both     # brief + self check
py -3 dryrun.py --agent-audit   # 向后兼容 = agent
```

### E.4 agent vs self check 阈值不同

- **self check**: 阈值固定 (e.g. 段首重复率 > 50% 红), 不分上下文
- **代理 check**: 阈值动态 (e.g. v15 P0-1 表9 数字偏差是 P0 一票否决级, 但 §5.2 单点偏差 < 5% 是 P2). worker 读 paper + result + 上下文, 判断 P0/P1/P2.

### E.5 SKILL.md 行数预算 (硬约束 ≤ 1500)

## F. 代理审计 brief 模板设计 (v1.5.7.38)

**核心**: agent_audit.py 输出 brief 让 mavis worker 独立 fresh 审计. brief 设计是审计质量的命脉.

### F.1 brief 4 段结构

1. **审计目标**: paper dir 路径 + 跑题项目根 + 审计时间 + 审计模式 (template / 跑题后内容审计)
2. **文件清单**: 13 章节 .tex + figures/ + 求解 .py + result xlsx + 中间图 + 数据 — worker 实际读这些
3. **审计 checklist (L1-L16 + 实战反例)**: 14 类 P0 反例 + AIGC 维度 + 数据/代码一致性 — worker 按此找问题
4. **报告输出格式**: P0/P1/P2 分类 + 数字一致性比对表 + 参考文献核验表 + 总耗时 — 标准化

### F.2 关键设计原则

- **每次 fresh**: brief 不缓存, worker 不复用主对话 context, 每次审计 fresh 调用
- **不要省略数字**: P0 项必须给复现值 (LP 复算 / 文件 mtime / 期刊数据库核验)
- **不要给模糊建议**: 修复必须给具体命令 (xelatex 命令 / sed 替换 / Python 脚本)
- **不要只看封面**: worker 必须读全部 13 章节 .tex + resultX.xlsx + planner.py
- **报告 ≤ 30 KB**: 重点突出 P0 (一票否决), 不要堆 P2 推荐

### F.4 mavis 主对话 orchestration

用户粘 brief → mavis (我) 识别"代理审计" 意图 → spawn mavis worker sub-session (用 task 工具, 独立 fresh context) → worker 实际读 paper + LP 复现 + 写报告 → 返回 mavis 主对话 → 用户.
